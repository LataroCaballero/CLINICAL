## Veredicto

El milestone cumple su definición de done. El flujo insignia se trazó end-to-end en código fuente y **cada hop es real**, no meramente plausible:

```
AutocompletePaciente (query sin match, allowCreate)
  → InlineCreatePaciente monta, precargado por buildPrefill()
  → submit nombre + DNI, telefono: ""
  → POST /pacientes  →  PacientesController.create()  →  PacientesService.create()
       normalizeTelefono("") → null
       etapaCRM: NUEVO_LEAD, flujo: null (forzados)
       prisma.paciente.create()
  → onCreated(pac) → onSelect → estado del modal (guardado por dialogSession vs dialogSessionRef)
  → POST /turnos { pacienteId }
       TurnosService.create(): etapaCRM NUEVO_LEAD → TURNO_AGENDADO (turnos.service.ts:154-159)
  → visible en agenda (useTurnosRango, incluye pacienteId/telefono) y en kanban CRM (getKanban)
```

Ningún paso exige teléfono. El seam 67↔69 (guards de envío) es sólido: los 5 entrypoints de envío WA llevan guard de cliente (`tieneTelefono`/`getMotivoBloqueoWhatsApp`) **y** aterrizan en el guard de servidor (`requireTelefonoParaEnvio()`), sin ruta de bypass. Los 4 endpoints de WhatsApp del controller están cubiertos.

Lo que sí amerita atención son **dos deudas pre-existentes de las que ahora dependen requisitos nuevos** — no son roturas introducidas por este milestone, pero cambiaron de criticidad al pasar a ser load-bearing.

## Tech Debt — Los 2 ítems que importan

### TD-01 — `POST /pacientes` sin ValidationPipe: mass-assignment + el mecanismo de TEL-01 no es el documentado

**Verificado independientemente en esta auditoría**, no heredado del subagente:
- `backend/src/main.ts:46` registra sólo `PrismaClientExceptionFilter`. Cero `useGlobalPipes`.
- `grep -rn "APP_PIPE" backend/src` → vacío.
- `pacientes.controller.ts:48-51` — `@Post() create(@Body() dto: CreatePacienteDto)`, sin pipe per-route.

Dos consecuencias, ambas confirmadas:

1. **`@IsOptional()` nunca corre.** El decorator que la Fase 67 agregó a `CreatePacienteDto` es inerte. TEL-01 funciona — pero por `normalizeTelefono()`, una función a mano independiente de class-validator, no por el DTO. El código no tiene bug; la *racionalización* documentada sí es incorrecta, y eso importa para el próximo que lea el schema y asuma que los decorators validan.

2. **Mass-assignment real.** `pacientes.service.ts:57` hace `{...dto, ...}` y los overrides explícitos (`etapaCRM`, `flujo`, `telefono`, las dos fechas) vienen *después* del spread, así que sólo esos 5 campos quedan protegidos. Cualquier otra columna de Prisma presente en el JSON del cliente se escribe verbatim: `usuarioId` (FK `String? @unique` que liga el paciente a una cuenta de login del portal), `whatsappOptIn`, `scoreConversion`, `crmArchivado`, `temperatura`, `motivoPerdida`.

**Pre-existente: sí.** El patrón `{...dto}` precede a las fases 67–69, y `NewPacienteModal → POST /pacientes` ya estaba expuesto con el mismo `@Auth('ADMIN','PROFESIONAL','SECRETARIA','FACTURADOR')`. La Fase 68 suma 3 entrypoints de UI al mismo endpoint ya expuesto — no baja la barra de autorización ni habilita un actor nuevo.

**Por qué igual amerita acción:** el repo ya conoce y aplica el fix. `paciente-portal.controller.ts` usa `new ValidationPipe({ whitelist: true })` per-route en 4 rutas, con comentarios que lo declaran "the load-bearing SC#3 guard — there is NO global ValidationPipe in this project". El módulo `pacientes` no lo tiene. Es una asimetría, no un descuido desconocido.

### TD-02 — ALTA-05 se sostiene sobre un `await` faltante

`pacientes.service.ts:75` — `return this.prisma.paciente.create({ data })` sin `await`, dentro del `try`. Por semántica de JS, el rechazo de una promesa retornada sin await no entra al `catch` circundante, así que la rama `P2002 → ConflictException('El DNI ingresado ya está registrado.')` de `:94-96` es **código muerto**. El propio comentario del código lo documenta (`:85-88`).

Lo que pasa realmente: el `PrismaClientKnownRequestError` crudo sube al `PrismaClientExceptionFilter` global (`main.ts:46`), que mapea `P2002` a HTTP 409 con el mensaje crudo de Prisma (`"Unique constraint failed on the fields: (\`dni\`)"`), no el texto en español.

Por qué ALTA-05 igual pasa: `InlineCreatePaciente.tsx:167` chequea `if (status === 409 || message?.includes("DNI"))`. La rama `status === 409` dispara sin importar el contenido del mensaje, así que el usuario ve el error inline correcto.

**Pre-existente: sí** (CR-03 de `67-REVIEW.md`, marcado y no arreglado). **Pero ALTA-05 es un requisito nuevo de este milestone**, así que la fragilidad pesa más hoy que antes: está a un refactor de romperse en silencio — por ejemplo si alguien "arregla" el catch del frontend para matchear sólo por `message.includes("DNI")`, o si alguien arregla el `await` y el mensaje amigable deja de contener "DNI".

Fix: agregar `await` al return (una palabra) revive la rama de 409 con mensaje en español, y entonces ambos lados del contrato dicen lo mismo.
